# Agent Guild RPG 设计文档

## 1. 产品概述

本项目是一款面向教学场景的像素风 Web 端 RPG Agent 世界，用于把学生学习和使用 Agent、构建系统、互测协作、完成课程关卡这件事游戏化。它不是纯娱乐 RPG，而是一个可承载真实课程运营的教学产品。

产品采用双层架构：

- 下层是真实教学系统，负责账号、课程、提交、评分、工会、授权、交易和任务。
- 上层是像素世界表现层，负责主城区、个人家园、工会大厅、聊天室入口、小人在线状态与建筑交互。

设计原则是：所有影响权限、评分、关卡、积分和奖励的逻辑，以业务后端为准；像素世界只负责游戏化入口和可视化表达。

## 2. 核心目标

- 支持老师与学生两类真实账号。
- 支持至少 40 名学生同时在线，每人拥有自己的家园与个人聊天室。
- 支持学生接入自己的 Agent，如 Codex、Claude Code 或未来其他 Agent。
- 支持 Day1-Day10 独立课程关卡，由老师控制解锁。
- 支持 Agent 代提交、Agent 初评、老师最终裁定的评分闭环。
- 支持学生创建工会、加入工会、开展内部协作与跨工会互测。
- 支持像素风主城区与外围家园世界结构，呈现“学习即冒险”的产品体验。

## 3. 账号与角色模型

### 3.1 真实账号

平台真实账号只有两种：

- `teacher`
- `student`

### 3.2 世界身份

以下身份不是独立账号类型，而是学生在具体关系中的世界身份：

- 会长
- 成员
- 授权访客
- 互测者
- 协作者

例如，会长只是某个学生在自己创建的工会中的关系身份，而不是平台全局角色。

## 4. 世界结构

### 4.1 世界地图

世界采用“主城区 + 外围个人家园”的结构：

- 主城区：承载工会大厅、任务板、会议空间、排行榜、交易台、关卡入口等公共功能。
- 外围家园：每位学生拥有一块独立家园区域，围绕主城区分布。

### 4.2 个人家园

每个学生家园至少包含：

- 个人聊天室
- 成长区或田地
- 个人作品入口
- 状态展示区

### 4.3 个人聊天室

个人聊天室是学生真实工作的地方，负责：

- 接入学生自己的 Agent
- 展示工作会话
- 支持按钮提交、对话触发提交、定时提交
- 配置授权访问

默认情况下，其他成员不能直接进入他人的聊天室，只有被授权后才可进入。

### 4.4 工会大厅

工会大厅位于主城区，是协作空间，不是个人生产空间。主要能力包括：

- 工会会议
- 工会任务板
- 成员状态查看
- 测试安排
- 贡献展示

### 4.5 课程关卡

Day1-Day10 作为独立 RPG 主线存在，不混在聊天室中，由老师统一控制解锁。

## 5. 核心用户流

### 5.1 学生日常流

1. 进入世界主页
2. 回到个人家园
3. 进入个人聊天室与 Agent 协作
4. 触发提交
5. 等待老师审核
6. 查看当天关卡进度和积分
7. 进入工会大厅参与协作或互测

### 5.2 老师运营流

1. 进入老师工作台
2. 查看待审核提交与班级总览
3. 审核 Agent 建议分
4. 调整或驳回异常结果
5. 解锁课程关卡
6. 发布任务或工会挑战

### 5.3 工会协作流

1. 学生创建工会
2. 其他学生申请加入
3. 工会内发起讨论、互测与协作任务
4. 需要时申请进入他人聊天室
5. 完成建议、调试、贡献记录
6. 获得协作点和工会积分

## 6. 前后端分离架构

### 6.1 总体结构

前端负责像素世界和交互表现，后端负责业务真相。

- 前端：世界地图、聊天室 UI、家园、工会大厅、老师工作台页面
- 后端：权限、课程、提交、评分、工会、授权、交易、任务、实时状态

### 6.2 推荐技术栈

- 前端应用壳：Next.js + React
- 像素世界层：Phaser 或同类 2D 引擎
- 后端 API：NestJS
- 数据库：PostgreSQL
- 缓存与实时：Redis
- 实时通道：WebSocket
- 异步任务：BullMQ、Redis Streams 或等价事件队列
- 文件与附件：对象存储

### 6.3 Agent 架构原则

平台不绑定某一家 Agent 厂商实现，而采用“统一内部模型 + 外部适配器”的架构。

内部统一抽象三个对象：

- `AgentSession`
- `AgentSubmission`
- `AgentCapability`

外部 Agent 通过适配器接入，优先兼容 MCP 与 A2A 这类开放分层思路。

### 6.4 40+ 在线设计原则

- 按房间模型进行实时广播，不做全局广播。
- 地图层只同步必要状态，如位置、动作、在线状态、忙碌状态。
- 提交、评分、奖励通过异步队列处理，不阻塞聊天室。
- 对老师工作台提供事件流和优先级排序，而非全量刷新。

## 7. 核心后端模块

- `Auth Service`：老师/学生登录与鉴权
- `World Service`：主城区、家园、房间、地图入口
- `Guild Service`：工会创建、加入、成员关系、工会任务
- `Chat Service`：个人聊天室、消息记录、授权访问
- `Agent Gateway`：外部 Agent 接入与会话映射
- `Submission Service`：统一接收三种提交入口
- `Review Service`：建议分、摘要、风险提示
- `Quest Service`：Day1-Day10 关卡定义、解锁和完成记录
- `Economy Service`：协作点、奖励、交易流水
- `Realtime Service`：在线状态、房间广播、状态同步
- `Observability Service`：日志、审计、追踪和告警

## 8. 数据模型

核心数据模型如下：

- `User`
- `CourseWorld`
- `Homestead`
- `Guild`
- `GuildMembership`
- `Room`
- `RoomAccessGrant`
- `QuestDay`
- `QuestProgress`
- `AgentSession`
- `AgentSubmission`
- `ReviewResult`
- `SystemCard`
- `TradeLedger`
- `ContributionLog`

这些模型共同构成平台的业务真相。

## 9. Agent 提交协议

### 9.1 提交入口

系统支持三种提交入口：

- 按钮触发
- 对话触发
- 定时触发

三者统一进入 `Submission Service`，不维护三套分叉逻辑。

### 9.2 提交结构

一次正式提交至少包含：

- `studentId`
- `courseWorldId`
- `dayId`
- `agentSessionId`
- `triggerType`
- `conversationSummary`
- `workSummary`
- `artifacts`
- `selfReflection`
- `agentEvaluationHints`
- `timestamp`

### 9.3 设计要求

- 提交必须绑定真实会话。
- 支持结构化摘要，不只存纯文本聊天。
- 支持附带代码、文档、截图、链接和命令摘要。
- 支持学生反思字段，以避免纯粹“让 Agent 代做”。

## 10. 评分流水线

评分采用 `Agent 初评 + 老师最终裁定` 双轨制。

### 10.1 流水线步骤

1. 接收提交
2. 组装评分上下文
3. 由评审 Agent 生成建议分、评分理由与风险标签
4. 老师在工作台进行通过、调分或驳回
5. 回写学生进度、奖励、工会贡献与排行榜

### 10.2 评分维度

- 对话质量
- 产出质量
- 理解与反思
- 协作贡献
- 成长表现

评分规则要求“有保底、无上限”。

### 10.3 Day1 特殊规则

Day1 不分工会，先完成首次 Agent 使用与首次提交。老师基于 Day1 表现观察后续工会分配。

## 11. 工会机制

### 11.1 工会定位

工会是学生组织层，不是平台真实账号体系的一部分。其核心价值在于：

- 带教
- 互助
- 互测
- 任务协作
- 建议交换
- 协作点积累

### 11.2 工会内部能力

- 会议讨论
- 任务板
- 授权协作
- 建议记录
- 贡献归属

### 11.3 跨工会能力

- 跨工会系统测试
- 系统能力调用
- 联合任务
- 有价值建议奖励

## 12. 协作点与交易系统

第一版不做重型自由市场，而采用轻量协作型经济系统。

交易介质统一命名为：`协作点`

### 12.1 协作点来源

- 提出有效建议
- 完成跨工会互测
- 帮助他人修复问题
- 被别人调用系统能力
- 完成工会任务

### 12.2 协作点用途

- 解锁特殊任务或展示位
- 工会内部奖励分配
- 荣誉展示与排行榜
- 后续世界化增强内容的兑换

## 13. 老师工作台

老师工作台是课程世界的运营中枢。

### 13.1 核心面板

- 今日总览
- 待审核队列
- 学生详情
- 工会运营面板
- 关卡控制面板
- 任务发布面板
- 异常处理面板

### 13.2 关键能力

- 快速审核和抽查
- 关卡解锁控制
- 工会观察和异常干预
- 发布课程任务和工会挑战

## 14. 实时在线设计

实时系统重点同步必要状态：

- 玩家在线状态
- 当前房间
- 小人动作状态
- 是否在会议中
- 是否忙碌或已提交

业务真相不依赖前端实时状态，而以后端记录为准。

## 15. 实施顺序

推荐按以下顺序推进：

1. 平台骨架
2. Agent 提交闭环
3. 工会系统
4. 授权协作与互测
5. 像素世界增强
6. 40+ 在线优化

设计原则是：

`能教 -> 能提 -> 能评 -> 能协作 -> 能沉浸 -> 能扩展`

## 16. V1 范围

### 16.1 必须进入 V1

- 老师/学生账号体系
- 课程世界与 Day1-Day10 配置结构
- 个人家园
- 个人聊天室
- Agent 接入适配层
- 三种提交入口
- Agent 初评 + 老师裁定
- 学生创建工会与加入工会
- 工会大厅与任务板
- 聊天室授权访问
- SystemCard
- 协作点与贡献流水
- 主城区与外围家园地图基础版

### 16.2 延后到 V1.5 或 V2

- 重型交易市场
- 自动化多 Agent 协同调用
- 深度家园装修
- 更复杂的会议演出效果
- 高级世界事件系统
- 复杂经济系统

## 17. 首版成功标准

- 老师可用于 40 人左右课程管理
- 学生可在个人家园与聊天室中接入自己的 Agent
- 学生可形成工会并开展协作
- Agent 可代提交，老师可快速审核
- Day1-Day10 可作为课程主线运行
- 产品整体表现为像素风教学 RPG 世界，而非传统后台

## 18. 风险与控制

### 18.1 主要风险

- Agent 接入不统一
- 评分规则不稳定
- 老师工作台信息过载
- 实时系统做得过重

### 18.2 控制策略

- 优先锁定提交协议、审核协议、授权协议、关卡配置协议
- 将评分与提交流程异步化
- 对老师工作台引入优先级、批量审核和摘要卡片
- 对实时系统只同步必要状态

## 19. 结论

这是一个以教学为核心、以 Agent 为原生能力、以像素 RPG 为体验壳的课程世界平台。其成功关键不在于先把地图做满，而在于先让“课程可运行、Agent 可提交、老师可评审、学生可协作”成立，再逐步增强世界表现与社交深度。
